## The problem

The platform needed to meet WCAG 2.2 A and AA for public-sector and regulated customers.

## What I did

- Audited 97 pages against every A and AA success criterion as a single source of truth, with a consistency check against the issue tracker.
- Traced most failures to shared components: ~450 failures became ~80 fixes in 23 themed PRs, grouped by theme (accessible names, keyboard and focus, reflow, motion) instead of one PR per page.
- Split the work with a colleague, then moved to a shared priority queue.
- Shipped fixes for:
  - Escape-to-dismiss (1.4.13), via a reusable hook in the design system
  - reflow at 320 px (1.4.10)
  - visible focus (2.4.7)
  - input purpose (1.3.5)
  - motion (2.2.2)
  - accessible names (4.1.2)
- Saved effort by testing a representative sample of pages for each fix instead of every page.
- Used Claude Code to write a reusable skill that rebuilds the project's status from its own tracking data: a burndown chart, the open decisions, the remaining PRs, and a forecast of when the work would finish, with a most-likely date and a range. A CEO-level update became a few minutes' work instead of a manual report.

### Why shared components first

A page-by-page approach would have meant hundreds of small, repetitive fixes, each reviewed separately. Fixing the shared component once fixed every page that used it, kept reviews focused on one theme at a time, and made the remaining work easy to forecast.
